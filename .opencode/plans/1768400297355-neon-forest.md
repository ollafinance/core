# StakingManager Implementation Plan

This plan covers issues #11, #12, #13 for implementing the StakingManager contract.

## Overview

The StakingManager is responsible for:
- Staking assets with the Aztec rollup using validator keys
- Initiating unstaking (withdrawal from rollup)
- Tracking staked principal and pending unstakes
- Harvesting sequencer rewards
- Managing a queue of validator BLS keys

**Source of truth**: `research/technical/architecture/` spec documents.

## Key Integration Points

### Aztec Contract Dependencies

The StakingManager interfaces with the actual Aztec protocol contracts from `contracts/dependencies/aztec-contracts-3.0.1/`:

### IStaking Interface (from Aztec contracts)

```solidity
// From @az/core/interfaces/IStaking.sol
interface IStakingCore {
    function deposit(
        address _attester,
        address _withdrawer,
        G1Point memory _publicKeyInG1,
        G2Point memory _publicKeyInG2,
        G1Point memory _proofOfPossession,
        bool _moveWithLatestRollup
    ) external;
    
    function initiateWithdraw(address _attester, address _recipient) external returns (bool);
    function finalizeWithdraw(address _attester) external;
    function flushEntryQueue() external;
    function flushEntryQueue(uint256 _toAdd) external;
}

interface IStaking is IStakingCore {
    function getActivationThreshold() external view returns (uint256);
    function getExit(address _attester) external view returns (Exit memory);
    function getStatus(address _attester) external view returns (Status);
    function getActiveAttesterCount() external view returns (uint256);
}
```

### IRollup Interface (for rewards)

```solidity
// From @az/core/interfaces/IRollup.sol
interface IRollupCore {
    function claimSequencerRewards(address _recipient) external returns (uint256);
}

interface IRollup is IRollupCore {
    function getSequencerRewards(address _sequencer) external view returns (uint256);
}
```

### Key Aztec Staking Concepts

1. **Entry Queue**: Validators don't activate immediately. They enter a queue via `deposit()` and are processed via `flushEntryQueue()`.

2. **Exit Flow**: Withdrawal has two phases:
   - `initiateWithdraw(_attester, _recipient)` - starts exit, creates Exit record with delay
   - `finalizeWithdraw(_attester)` - after delay, transfers funds

3. **Validator States** (from `StakingLib.Status`):
   - `NONE` - Not registered
   - `VALIDATING` - Active validator
   - `ZOMBIE` - Slashed, has funds but not validating
   - `EXITING` - In withdrawal process

4. **Exit Struct**:
   ```solidity
   struct Exit {
       uint256 withdrawalId;
       uint256 amount;
       Timestamp exitableAt;
       address recipientOrWithdrawer;
       bool isRecipient;
       bool exists;
   }
   ```

## Implementation Order

1. **Phase 1** (Issue #13): Create all supporting files first:
   - `QueueLib.sol` - FIFO queue library for KeyStore (using `@az` BN254 types)
   - `IStakingManager.sol` - Expanded interface with all types/events/errors (import `@az` types)
   - `MockAztecRollup.sol` - Mock implementing `IStaking` interface for testing
   - `StakingManager.sol` - Core contract with access control and placeholders
   - `StakingManager.t.sol` - Unit tests for core functionality

2. **Phase 2** (Issue #12): Implement stake flow:
   - Update `_stakeInternal()` with full logic
   - Add active validator tracking
   - Add stake flow tests

3. **Phase 3** (Issue #11): Implement unstake flow:
   - Add `UnstakeRequest` struct and tracking
   - Update `_unstakeInternal()` with full logic
   - Update `_claimUnstakedFunds()` with full logic
   - Add unstake flow tests
